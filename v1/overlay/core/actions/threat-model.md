# Action: threat-model
Intent/scope: Threat model a design before code exists: assets, actors (including AI agents with repository or infrastructure access), data flow and trust boundaries, STRIDE threats with concrete step-by-step scenarios, business abuse cases (account enumeration, cross-tenant access, duplicate credit use, payment fraud), supply chain, derived verifiable security requirements and accepted risks, in the form of templates/threat-model.md. Without arguments model the current architecture document.
Responsible specialist: security; principal routes, questions and consolidates. Consult architect for the design and privacy-compliance when personal or health data is involved. This is design-time analysis and does not replace the security gate on the implemented change.
Input: requirements, architecture and decisions, hosting design, data classification, project profiles, permitted paths and snapshot.
Output: threats with stable IDs, likelihood, impact, mitigation, how to verify it and owner; requirements ready to become acceptance criteria; risks left open for explicit human acceptance. A threat without a concrete scenario or a mitigation without a verification method is not accepted. Common policies and workflow apply to standalone invocations too.
